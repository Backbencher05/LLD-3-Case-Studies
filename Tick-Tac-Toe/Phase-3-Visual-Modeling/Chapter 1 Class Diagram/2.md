# What must a single class communicate?

A class exists to answer one fundamental question:

> **"If this object existed in the system, what should I know about it before I read its implementation?"**

That breaks into a few essential pieces.

---

## 1. Identity — "Who are you?"

The first thing any engineer needs is the identity.

Not because of syntax.

Because without identity, nothing else has a reference point.

Example:

```
Game
```

Immediately the reader knows what we're discussing.

Without identity, every other piece of information becomes meaningless.

### Why first?

Everything else describes *this* thing.

Identity is the anchor.

---

## 2. Purpose — "Why do you exist?"

Knowing a name isn't enough.

Imagine seeing:

```
WinningCondition
```

That raises another question:

> Why does this object exist?

Its purpose might be:

> Determines whether the game has been won.

This is the object's reason for existing.

### Why second?

Architecture is about **responsibility**, not about names.

Two classes can have similar names but completely different responsibilities.

Purpose prevents misunderstanding.

---

## 3. State — "What do you know?"

Every object remembers something.

That remembered information is its state.

For example:

Game remembers

* current turn
* status
* players
* board

Board remembers

* cells

Cell remembers

* symbol

Notice something important.

These are not arbitrary variables.

They are the minimum information required for the object to fulfil its purpose.

### Why third?

Purpose tells us *why* the object exists.

State tells us *what it must remember* to fulfil that purpose.

---

## 4. Responsibilities (Capabilities) — "What can you do?"

An object is not just stored information.

It performs work.

For example:

Game

* start game
* make move
* switch turn
* end game

Board

* place symbol
* validate position

WinningCondition

* check winner

Notice we're not talking about method signatures.

We're talking about **capabilities**.

### Why fourth?

Once we know:

* who it is,
* why it exists,
* what it knows,

the natural next question is:

> "What actions is it responsible for?"

This is behaviour from an architectural perspective, not an implementation perspective.

---

## 5. Invariants / Rules — "What must always remain true?"

This is something many engineers forget.

Every meaningful object has rules that define its correctness.

Examples:

Cell

* may contain at most one symbol

Board

* cannot contain positions outside its dimensions

Game

* only one player has the turn at any moment
* once finished, no further moves are accepted

These are not algorithms.

They are truths.

### Why include them?

Because invariants explain the object's contract.

Without them, an engineer cannot judge whether the object is in a valid state.

---

# In What Order Should Information Be Presented?

The order should mirror how humans naturally build understanding.

| Order | Information      | Why this comes now                   |
| ----- | ---------------- | ------------------------------------ |
| 1     | Identity         | Gives the object a reference point   |
| 2     | Purpose          | Explains why it exists               |
| 3     | State            | Shows what it must remember          |
| 4     | Responsibilities | Shows what it is expected to do      |
| 5     | Invariants       | Defines the rules that keep it valid |

Notice how each layer depends on the previous one.

You cannot judge state until you know the purpose.

You cannot judge responsibilities until you know the state.

You cannot judge correctness until you know all of them.

This creates a logical progression instead of a random list of facts.

---

# What Should NOT Be Inside a Class Representation?

This is just as important.

A class representation should describe **the class itself**, not the entire system.

Anything that only makes sense when two or more classes are considered belongs elsewhere.

Let's classify those.

---

## 1. Relationships

Examples:

* Game owns Board
* Board contains Cells
* Game uses WinningCondition

These do not describe the class in isolation.

They describe how classes interact.

Therefore they belong in a system-level structural view.

---

## 2. Collaboration Flow

Examples:

```
Player
 ↓
Game
 ↓
Board
 ↓
WinningCondition
```

This is not a property of any one class.

It describes cooperation between multiple objects.

It belongs in interaction modelling.

---

## 3. Object Creation

Questions like:

* Who creates Board?
* Who creates Player?
* Who injects WinningCondition?

These concern object lifecycle and dependency management.

They are architectural decisions across the system, not intrinsic properties of a single class.

---

## 4. Algorithms

Examples:

* winner detection logic
* minimax
* board traversal

Algorithms explain **how** responsibilities are fulfilled.

A class representation should communicate **what** the class is responsible for, not the detailed procedure.

---

## 5. Execution Order

Examples:

```
validate
↓

place move
↓

check winner
↓

switch turn
```

This is runtime behaviour.

A class is static.

Execution order belongs in behavioural models.

---

## 6. Deployment or Infrastructure

Examples:

* stored in Redis
* persisted to PostgreSQL
* exposed via REST API

These describe where the software runs or how it is deployed.

They do not change the conceptual identity of the class.

---

# A Powerful Observation

Look at what we've built:

### Inside a class

* Identity
* Purpose
* State
* Responsibilities
* Invariants

These answer:

> **"What is this object?"**

### Outside the class

* Relationships
* Ownership
* Collaboration
* Creation
* Algorithms
* Execution flow
* Infrastructure

These answer:

> **"How does this object live and work within the larger system?"**

That separation is profound.

One describes the object.

The other describes the ecosystem.

Confusing the two is what makes diagrams noisy and hard to understand.

# The Discovery We've Just Made

Without ever mentioning rectangles, compartments, or UML, we've naturally separated software modelling into two complementary views:

| Focus                           | Core Question                               | Information                                                              |
| ------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------ |
| **Class (Object View)**         | *What is this object?*                      | Identity, purpose, state, responsibilities, invariants                   |
| **System (Collaboration View)** | *How does this object fit into the system?* | Relationships, ownership, creation, collaboration, execution, algorithms |

This is the mental foundation upon which class diagrams are built. UML didn't invent these ideas—it simply provided a standard notation for communicating them.

> **A class representation should communicate everything another engineer needs to understand the object itself, and nothing that only becomes meaningful when multiple objects begin working together.**

# Engineering Handbook

## Business Question

> Why doesn't a class diagram communicate everything about a class?

## Final Discovery

> **A class diagram is responsible only for communicating the static structure of a system. Behaviour, intent, lifecycle, and implementation details are communicated through other engineering representations.**

## Why This Discovery Is Necessary

Trying to communicate every aspect of a system in one diagram leads to noise, ambiguity, and poor communication.

Professional engineering separates concerns not only in code, but also in documentation and visual models.

## Engineering Checklist

Before adding information to a class diagram, ask:

* Does this describe the system's static structure?
* Will it help another engineer understand the architecture?
* Or does it belong in a behavioural, lifecycle, or documentation view?

If it belongs elsewhere, resist the temptation to overload the class diagram.

---

# Interview Thinking

If an interviewer asks:

> **"Why are there different UML diagrams?"**

A memorised answer lists the diagrams.

An architect answers:

> "Because no single representation can communicate every aspect of a software system effectively. Each diagram has a specific responsibility. A class diagram communicates static structure, a sequence diagram communicates interactions over time, and a state diagram communicates lifecycle. Together, they provide complementary views of the same design."

That answer demonstrates architectural reasoning rather than UML knowledge.
