# The Goal of the Diagram

The goal is **not** to show code.

The goal is **not** to impress people with UML.

The goal is to transfer the **mental model** of the system.

That is the architect's job.

A good diagram doesn't teach syntax.

It teaches how the system thinks.

---

# After Seeing the Diagram, the Engineer Should Be Able To Answer

## 1. What are the important objects?

Not variables.

Not methods.

Objects.

For Tic-Tac-Toe they should immediately know there are things like:

* Game
* Board
* Player
* Cell
* Move
* WinningCondition

The first understanding is:

> "These are the living objects inside this software."

---

## 2. What does each object own?

They should know

Who is responsible for what.

Not implementation.

Responsibilities.

For example they should understand

Game controls gameplay.

Board manages cells.

Player makes moves.

WinningCondition checks victory.

Cell stores one symbol.

Immediately they should understand

> "Every object has its own job."

---

## 3. How are these objects connected?

This is probably the biggest question.

Without reading code they should know

Game has a Board.

Board contains Cells.

Game has Players.

Move belongs to Player.

WinningCondition works with Board.

Immediately they understand

> "How the system is composed."

---

## 4. Who depends on whom?

Very important.

They should know

Who talks to whom.

Who should never know about whom.

For example

Game knows Board.

Board doesn't know Game.

Cell doesn't know Player.

Player doesn't know Board internals.

This immediately tells them

Coupling.

---

## 5. Who owns what?

Ownership is different from association.

For example

If Game dies...

Board dies.

Cells die.

Moves disappear.

Players may or may not survive depending on design.

The engineer immediately understands object lifetime.

---

## 6. Where does behaviour live?

A good engineer immediately asks

"If a player makes a move...

which object should handle it?"

The diagram should answer this.

Without code they should roughly predict

Game validates turn.

Board updates cell.

WinningCondition checks victory.

Game changes state.

If they can predict behaviour...

they already understand the architecture.

---

## 7. What are the boundaries?

They should immediately know

Which object should NOT do something.

For example

Cell should not decide winners.

Player should not update board directly.

Board should not decide whose turn it is.

Game should not store coordinate logic inside itself.

Boundaries become visible.

---

## 8. How does data flow?

Without reading code they should roughly imagine

```
Player

    ↓

Game

    ↓

Board

    ↓

Cell

    ↓

WinningCondition

    ↓

Game State Updated
```

They can almost visualize execution.

---

## 9. What can change independently?

An architect always asks

"If tomorrow we support 5×5 board...

what changes?"

"If tomorrow we support four players?"

"If tomorrow we support different winning rules?"

The diagram should help answer

Which object changes.

Which object stays untouched.

This is architecture.

---

## 10. What is the philosophy of the design?

This is the deepest understanding.

After looking at the diagram they should feel something like

> "This system is object-oriented."

or

> "Responsibilities are clearly separated."

or

> "Game orchestrates everything."

or

> "Winning logic is isolated."

The diagram should communicate the design philosophy without anyone saying it aloud.

---

# What Should NOT Happen

After looking at the diagram, the engineer should **not** think:

* "I don't know where moves happen."
* "Everything seems connected to everything."
* "Why does Player know Cell?"
* "Why does Board know Game?"
* "Who is responsible for validation?"
* "Where is the game state stored?"

If those questions remain, the diagram has failed.

---

# The Architect's Objective

When an architect draws a class diagram, the hidden goal is:

> **Transfer the software's mental model from one engineer's mind to another with as little ambiguity as possible.**

The diagram is successful when the new engineer can answer questions like:

* What objects exist?
* Why does each object exist?
* Who owns what?
* Who collaborates with whom?
* Who is responsible for each decision?
* What can change independently?
* Where should new features be added?
* What should never be modified?

Notice that none of these answers require reading a single line of code.

---

# One Sentence That Changes the Thinking

> **A class diagram is not a picture of classes—it is a map of the software's thinking, showing how responsibilities, relationships, and collaboration are organised so another engineer can reason about the system before ever reading the code.**

# A Hidden Discovery

Now I want to connect this back to something we've been using throughout our journey.

Remember our Software Discovery Framework (SDF)?

It asks five questions:

1. Who owns the responsibility?
2. What work must it perform?
3. What knowledge must it remember?
4. Who must it collaborate with?
5. Who owns its lifecycle?

Now compare that to what a class diagram should communicate.

| SDF Question                     | Class Diagram Communicates                        |
| -------------------------------- | ------------------------------------------------- |
| Who owns the responsibility?     | Classes and their responsibilities                |
| What work must it perform?       | Operations (at a high level)                      |
| What knowledge must it remember? | Attributes                                        |
| Who collaborates over time?      | Relationships                                     |
| Who owns its lifecycle?          | Ownership, composition, aggregation, associations |

Do you notice something remarkable?

**A class diagram isn't a new activity.**

It is simply a **visual representation of the discoveries we've already made**.

This is a major milestone in your engineering mindset.

A beginner thinks:

An experienced engineer thinks:

> "First I design. The class diagram is evidence of that design."

# Another Hidden Insight

You wrote:

> "The engineer should predict behaviour."

This deserves special attention.

A class diagram does **not** show runtime execution.

That's the purpose of a Sequence Diagram, which we'll study next.

However, a good class diagram should allow an engineer to make *reasonable predictions* about runtime behaviour because responsibilities are clearly assigned.

For example, seeing that `Game` collaborates with `Board` and `WinningCondition`, an engineer can infer that a move will likely be validated by `Game`, applied to `Board`, and then checked by `WinningCondition`.

So the class diagram doesn't describe the execution—it makes the execution understandable.

---

# One Small Refinement

This statement:

> "How does data flow?"

is slightly misleading in the context of a class diagram.

Data flow is primarily a behavioural concern.

A class diagram focuses on **static structure**.

A better wording would be:

> "How do objects collaborate?"

or

> "Which objects are expected to communicate?"

We'll explore actual message flow when we reach Sequence Diagrams.

# Engineering Principle (Handbook)

## Business Question

> Before writing code, how can one engineer transfer the architecture of a software system to another engineer?

## Final Discovery

> **A class diagram is the visual representation of an already-discovered software design. It communicates the system's static structure—its responsibilities, knowledge, relationships, and ownership—so another engineer can understand how the software is organised before reading any code.**

## Why This Discovery Is Necessary

Without a shared structural model:

* Engineers interpret the system differently.
* Responsibilities become blurred.
* Coupling increases.
* New features are added inconsistently.
* Architecture slowly degrades.

A class diagram provides a common mental model.

## Engineering Mindset

> **Never draw classes to discover your design. Draw classes to communicate the design you have already discovered.**

---

# Interview Thinking

If an interviewer asks:

> **"What is a class diagram?"**

Avoid the textbook answer:

> "A class diagram shows classes and relationships."

Instead, explain the purpose:

> "A class diagram is a communication tool that captures the static architecture of a system. It shows the key objects, the responsibilities they own, the knowledge they maintain, and how they collaborate, allowing engineers to reason about the design before looking at the implementation."

That answer demonstrates architectural thinking rather than memorisation.
